// 1950s

Code was holes in cardboard.

Finding bugs? Sharing work? Good luck deciphering a matrix of holes.

Back in the 1950s, computer scientists used punch cards. Literal cardboard cards that they would punch holes in. Dont ask me how it worked..I wasn’t born then, but to my understanding this is how they would make changes in the code. Finding bugs, sharing your work..had to be a pain because they had to decipher from a matrix of holes.
// 1980s–90s

Code went digital.

Teams grew. Developers started stepping on each other's toes and overwriting each other's work.

shared-drive/main.c[09:14] alice saved main.c [09:15] bob saved main.c [09:16] alice wait… where did my code go??
Luckily, in the 1980s/1990s things went digital but a new problem arose. As engineering teams grew, developers started stepping on each other's toes, constantly overwriting each other's work..
// RCS · Revision Control System

Check it out.
Lock it down.

While you held the key, no one in the company could touch that file.

alice@workstation$ co -l main.c main.c --> checked out, 🔒 locked bob@workstation$ co -l main.c co error: main.c locked by alice

No more stepped-on toes. But slow af.

So they invented RCS (Revision Control System). If you wished to change a file, you had to check it out and lock it down. While you held that key, no one in the company could touch it. This avoided the issue of stepping on each others toes but it made work slow af .
// CVS & Subversion

Everyone works at the same time.

Grab a copy from the central server, work at your own desk. Until you and a teammate change the exact same line.

svn update — conflict in cart.c<<<<<<< .mine total = price * qty; ======= total = price * qty * tax; >>>>>>> .r42 C cart.c ← you fix it
So they created version control systems such as CVS and Subversion (SVN). Now, everyone could request a copy of the files from a central server and work at their own desks simultaneously. Of course if you and a teammate changed the exact same line at the same time, a conflict would occur and you had to fix it.
// how it works

Centralized version control

  • One main copy of the code lives on a central server.
  • Everyone connects to that server to make and share changes.
  • Server goes down → collaboration stops.
Here’s how central version control works: • There's one main copy of the code on a central server. * Everyone connects to that server to make and share changes. * If the server goes down, collaboration is disrupted.
// fast forward to 2005

Linux: a huge open source project, built by people all over the world.

Instead of a centralized system, they used a distributed one called BitKeeper, a paid, licensed platform.

Fast forward to 2005, and the linux operating system is born. It’s this huge open source project (still huge today) and people all over the world were building it it. Instead of using a centralized version control system, they had to use a distributed version control system called Bitkeeper. Bitkeeper was a paid licensed platform. This was preferred because:
// why distributed won

Distributed version control

  • Everyone has their own complete copy of the code and its history.
  • Make changes and commits without internet.
  • Sync with others when you're ready.
Everyone has their own complete copy of the code and its history. You can make changes and commits without internet access. You sync your changes with others when you're ready.
